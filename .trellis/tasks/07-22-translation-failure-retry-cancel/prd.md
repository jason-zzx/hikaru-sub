# 翻译失败可见、重试与取消

## Goal

让用户能准确识别翻译的完整成功、部分失败和主动取消状态，并在不丢失已完成译文的前提下仅重试未完成条目或保存当前结果。

## Background

- `src/services/translation/types.ts` 已返回 `successCount`、`failedCount` 和 `errors`。
- `src/services/translation/base.ts` 在批次失败后降级为逐条翻译，但主动取消尚未贯穿批次、回退和 HTTP 请求。
- `src/components/workflow/TranslateView.tsx` 当前仅将部分失败写入 `console.warn()`，仍显示“翻译完成”并保存字幕。
- `src/services/translation/requestScheduler.ts` 只有并发与 RPM 调度，没有清空排队请求或终止在途请求的用户取消链路。

## Requirements

### R1. 明确展示结果状态

- 完整成功时显示成功状态及“成功 N 条、失败 0 条”。
- 部分失败且至少成功一条时显示独立的部分完成状态及“成功 N 条、失败 M 条”，不得显示完整成功文案。
- 成功 0 条且失败大于 0 条时显示“翻译失败”，不得显示“翻译部分完成”。
- 主动取消时显示取消状态及当时已完成的成功/失败数量，不得作为普通错误或完整成功处理。
- 状态栏任务状态必须与页面状态一致；部分失败或取消不能标记为 `success`。

### R2. 失败原因可见且安全

- 部分失败或取消后允许用户展开查看失败原因。
- 已知的 API Key、Authorization、请求正文、字幕原文、术语表、自定义 prompt 和 system/user prompt 值必须先做不区分大小写的精确打码。
- 翻译错误展示应用生成的受控类别、批次/条目位置和 HTTP 状态；结构化服务端错误字段只有在打码、残余重叠检查与长度限制后才可附加展示。精确打码后若仍与 API credential/Authorization 存在至少 4 个连续字符重叠，或与请求正文、字幕、术语表、custom/system/user prompt 存在至少 8 个连续字符重叠，则丢弃整个服务端原因。
- 不得展示非 JSON generation API 响应正文或任意未分类异常文本。
- 展示内容应有长度和条数上限；每个敏感区段统一用单个 `***` 打码，并合并连续掩码；取消本身不重复生成每条失败错误。

### R3. 仅重试未完成条目

- 部分失败或取消后提供“重试失败条目”。
- 重试输入只包含当前没有有效 `secondaryText` 的源 cue。
- 重试结果按 cue `id` 合并进现有逻辑结果，保留此前成功译文和源 cue 顺序。
- 重试可再次部分失败或取消，并刷新累计成功/失败计数及失败原因。

### R4. 取消排队与在途请求

- 翻译中提供“取消翻译”。
- 一次取消动作必须停止尚未启动的调度队列，并通过同一取消信号终止所有在途 provider HTTP 请求。
- 取消只在网络请求阶段可用；请求阶段结束后立即关闭取消入口，再进入应用/保存阶段。
- 已接受的主动取消不得继续自动应用 project store 或写入译文文件，也不得触发批次失败后的逐条翻译降级。
- 页面卸载或工作视频切换时必须终止该页面发起的翻译，避免后台继续请求或将过期结果写入当前文档。

### R5. 不完整结果由用户决定保存

- 完整成功继续沿用现有自动保存行为。
- 部分失败和主动取消均不得自动写入 `*.translated.ass` 或覆盖 project store；只在翻译页面内保留当时已完成的译文。
- 部分失败或取消后由用户选择“保存当前结果”或“重试失败条目”。
- 显式保存仍须执行未保存字幕确认，并沿用现有逻辑 cue → `subtitleMergeMode` 序列化 → 物理 ASS 行 → project store/译文文件流程，以及文档过期保护、恢复快照处理和保存 token 配对。

### R6. 供应商错误快速失败

- 自动逐条 fallback 只用于 provider envelope 有效、且同一批次连续 2 次本地批量索引/translation JSON 校验失败；第一次失败先原样重试批次，第二次仍失败才通过单条纯文本响应挽救。
- HTTP 错误、超时、网络异常不得放大为逐条请求。
- 确定性错误立即停止：HTTP `400/401/403/404/405/410/413/415/422` 及 provider response envelope 无效。
- 瞬时错误允许当前运行继续：HTTP `408/409/425/429/5xx`、超时和网络异常。每个批次遇到瞬时错误时原样重试 1 次，第二次仍失败才将该批次计为失败工作单元；共享失败 streak 按工作单元完成顺序更新，两个重试耗尽的失败工作单元完成且其间没有成功工作单元完成时停止排队和在途请求，任何成功工作单元完成都会清零该 streak。此规则独立于同一批次按顺序执行的两次格式校验失败与 fallback。
- 批量 JSON 校验失败进入 fallback 后，每个单条请求遇到瞬时错误时也原样重试 1 次，第二次仍失败才将该条计为失败；确定性错误与主动取消均不重试。
- 内部快速停止不显示为用户主动取消；已完成批次仍保留，错误摘要仍使用受控类别。

### R7. 切页取消状态可见

- 离开翻译页仍须取消当前页面发起的翻译，不在后台继续。
- 因离开翻译页或切换工作视频而取消时，全局任务消息须明确说明不会在后台继续运行，且在状态栏和重新进入翻译页后均可见；用户在页面内手动取消可保留简洁的成功/失败计数消息。
- 本任务不跨页面保留未保存的部分译文；需要跨页面恢复逻辑草稿时另行设计 session-keyed store。

### R8. 翻译页自适应滚动

- 翻译页内容高度超过工作区时，页面主内容区域须纵向滚动，不能被 AppLayout 的 `overflow-hidden` 裁切。
- 页面仍须占满可用空间，并避免横向滚动或破坏底部操作区。

## Acceptance Criteria

- [ ] 全部条目成功时，页面显示准确计数和完整成功状态，并正常生成、加载和保存双语 ASS。
- [ ] 至少一条成功且至少一条失败时，页面显示“翻译部分完成”及准确计数；成功 0 条时显示“翻译失败”，均提供可展开的安全错误摘要，且不自动写入译文文件或 project store。
- [ ] 点击“重试失败条目”后，只向 provider 发送未完成 cue；成功结果按 `id` 合并，已成功译文和顺序不变。
- [ ] 点击“取消翻译”后，排队请求不再启动，在途 `fetch` 被 abort，不启动逐条 fallback，且该次已接受的取消不会随后自动应用或写入结果。
- [ ] 取消完成后，页面保留已完成译文，提供“保存当前结果”和“重试失败条目”；取消本身不显示为普通失败，也不自动写入译文文件或 project store。
- [ ] 部分失败或取消后点击“保存当前结果”，会重新确认未保存字幕，再按既有 ASS 边界应用 project store 并写入 `translatedAssPath`；零条成功译文时不能保存。
- [ ] 页面卸载或会话切换不会继续发送翻译请求，也不会把旧结果应用到新文档；状态栏及重新进入翻译页后明确显示翻译已取消且不会后台继续。
- [ ] 同一批次第一次本地批量索引/translation JSON 校验失败时原样重试批次，第二次仍校验失败才逐条 fallback；批次与 fallback 单条遇到瞬时错误均原样重试 1 次，第二次仍失败才计为该工作单元失败；确定性错误立即停止且不重试。
- [ ] 共享瞬时失败 streak 按工作单元完成顺序计算：两个重试耗尽的失败工作单元完成且其间没有成功工作单元完成时才停止其余请求，任一成功工作单元完成都会清零 streak；同一批次的格式重试仍按顺序执行，只有连续两次格式校验失败才进入 fallback。
- [ ] 页面错误详情只精确打码已知敏感值；精确打码后若仍与 API credential/Authorization 有 4+ 字符重叠，或与请求正文、字幕、术语表、custom/system/user prompt 有 8+ 字符重叠，则不显示结构化服务端原因；非 JSON 响应正文和任意未分类异常不直接显示。
- [ ] 翻译状态使页面内容超出工作区高度时，翻译页可纵向滚动且底部操作可访问。
- [ ] 翻译服务相关单测、目标页面逻辑测试和 `pnpm build` 通过。

## Out of Scope

- 跨页面或应用重启后恢复翻译任务。
- 自动重试次数、指数退避、失败原因分类筛选或单条手动选择重试。
- 修改 provider 配置、翻译 prompt、字幕合并模式或 Tauri/Rust 后端。
